# Backtester Design Notes

## Overview

To apply an event-driven approach to a backtesting system it is necessary to define our components (or objects) that will handle specific tasks:

- **Event** — The Event is the fundamental class unit of the event-driven system. It contains a type (such as "MARKET", "SIGNAL", "ORDER" or "FILL") that determines how it will be handled within the event-loop.
- **Event Queue** — The Event Queue is an in-memory Python Queue object that stores all of the Event sub-class objects that are generated by the rest of the software.
- **DataHandler** — The DataHandler is an abstract base class (ABC) that presents an interface for handling both historical or live market data. This provides significant flexibility as the Strategy and Portfolio modules can thus be reused between both approaches. The DataHandler generates a new MarketEvent upon every heartbeat of the system.
- **Strategy** — The Strategy is also an ABC that presents an interface for taking market data and generating corresponding SignalEvents, which are ultimately utilised by the Portfolio object. A SignalEvent contains a ticker symbol, a direction (LONG or SHORT) and a timestamp.
- **Portfolio** — This is an ABC which handles the order management associated with current and subsequent positions for a strategy. It also carries out risk management across the portfolio, including sector exposure and position sizing. In a more sophisticated implementation this could be delegated to a RiskManagement class. The Portfolio takes SignalEvents from the Queue and generates OrderEvents that get added to the Queue.
- **ExecutionHandler** — The ExecutionHandler simulates a connection to a brokerage. The job of the handler is to take OrderEvents from the Queue and execute them, either via a simulated approach or an actual connection to a live brokerage. Once orders are executed the handler creates FillEvents, which describe what was actually transacted, including fees, commission and slippage (if modelled).
- **The Loop** — All of these components are wrapped in an event-loop that correctly handles all Event types, routing them to the appropriate component.

Primary use case: factor-model-based equity strategy backtesting.
Design goal: generic enough to extend later (other asset classes, strategy types, frequencies).

---

## 1. Event Loop & Core Components

```
DataHandler → [MarketEvent] → Strategy → [SignalEvent] → Portfolio → [OrderEvent] → ExecutionHandler → [FillEvent] → Portfolio
```

### Open questions

  - Sync (simple `while queue` loop): easier to reason about, sufficient for daily/minute data

  - Typed dataclasses per event kind (MarketEvent, SignalEvent, OrderEvent, FillEvent): explicit, type-safe, easy to validate

  - Each component pair has its own queue/channel (cleaner boundaries, harder to trace)

---

## 2. Event Types

Minimum set for an equity backtester:

| Event | Produced by | Consumed by |
|---|---|---|
| `MarketEvent` | DataHandler | Strategy |
| `SignalEvent` | Strategy | Portfolio |
| `OrderEvent` | Portfolio | ExecutionHandler |
| `FillEvent` | ExecutionHandler | Portfolio |

### Open questions

- **Corporate actions** (dividends, splits, spinoffs): handle as events, or pre-adjust prices in the data layer?
- **RebalanceEvent**: explicit rebalance trigger vs. strategy always re-evaluating on every MarketEvent?
-> rebal on every event, then buy if drift is large enough
- **ScheduledEvent**: cron-like triggers for end-of-month rebalances, earnings blackouts, etc. — or handled inside the strategy?
-> no live trading for now
- **RiskEvent**: separate event when a risk limit is breached, or inline checks inside Portfolio?
-> seperate RiskManagement module doing the observing

## 3. Data Layer (DataHandler)

### Open questions

- **Data granularity**: daily OHLCV only to start, or support intraday (minute, tick) from day one? (Tick data changes the architecture significantly — e.g., you need bid/ask spreads, not just close prices.)
-> for now close prices in parquet 

- **Data sources**: where does market data come from?
  - Local CSV / Parquet files
  - A database (e.g., DuckDB, Postgres, TimescaleDB)
  - API (Polygon, Alpaca, Bloomberg, Refinitiv)
  - Combination via an adapter pattern

- **Universe management**: how do you define and update the investable universe over time?
  - Static universe (fixed list of tickers)
  - Dynamic (e.g., S&P 500 constituents at each point in time — requires point-in-time data to avoid survivorship bias)

- **Survivorship bias**: do you need point-in-time constituent data, or is a static universe acceptable for your use case?

- **Factor data**: does factor data (e.g., P/B, momentum scores) live in the DataHandler alongside price data, or in a separate FactorHandler?

- **Look-ahead bias prevention**: how strictly does the DataHandler enforce that the strategy only sees data available at each timestamp?
  - Lazy iterator (yields one bar at a time, strategy can't peek ahead)
  - Snapshot approach (full history available, strategy must respect a "current date" cursor)

---

## 4. Strategy / Signal Generation

For factor models specifically, the strategy layer is essentially: compute factor scores → rank universe → generate target weights.

### Open questions

- **Signal granularity**: does the strategy output raw signals (factor scores), ranked signals (decile), or target weights directly?

- **Single-strategy vs multi-strategy**: should the backtester support running multiple strategies simultaneously (e.g., long/short, sector-neutral legs) and combining their signals?

- **Factor computation**: does factor calculation happen inside the strategy, or is it a preprocessing step that produces a factor DataFrame fed into the backtester?

- **Rebalance frequency**: how does the strategy communicate rebalance timing? (Calendar-based, signal-threshold-based, or event-triggered?)

---

## 5. Portfolio Construction

### Open questions

- **Position sizing**: how do target weights get translated to share quantities?
  - Equal weight
  - Factor-score-proportional weight
  - Risk-parity / volatility-scaled
  - Mean-variance optimization (requires a covariance model)

- **Constraints**: where do portfolio constraints live?
  - Long-only vs long-short
  - Sector/industry neutrality
  - Max position size, turnover limits
  - Leverage limits
  - Should these be parameters on Portfolio, or a separate PortfolioOptimizer component?

- **Cash management**: does the portfolio hold a cash buffer, or is it always fully invested?

- **Rebalancing logic**: full rebalance to target weights vs. threshold-based rebalancing (only trade if drift > X%)?

---

## 6. Execution / Broker Simulation

### Open questions

- **Order types supported**: market orders only to start, or limit/stop orders too?

- **Slippage model**: how realistic does execution simulation need to be?
  - Fixed bps per trade
  - Volume-based (e.g., fraction of ADV)
  - Bid-ask spread model
  - Market impact model (e.g., square-root law)

- **Commission model**: fixed per trade, per share, or percentage of notional?

- **Fill assumption**: fill at close price, open price, or VWAP of next bar?

- **Partial fills**: does the simulation need to handle partial fills (e.g., illiquid names)?

---

## 7. Risk Management

### Open questions

- **Pre-trade vs post-trade checks**: does the risk layer run before orders are submitted (blocking), after fills are received (alerting), or both?

- **Risk metrics to enforce in real-time**: position limits, gross/net exposure, sector concentration, VaR?

- **Integration point**: separate RiskManager component that sits between Portfolio and ExecutionHandler, or risk checks embedded inside Portfolio?

---

## 8. Performance & Analytics

### Open questions

- **What metrics matter most?**
  - Returns: total, annualized, cumulative
  - Risk: volatility, max drawdown, drawdown duration
  - Risk-adjusted: Sharpe, Sortino, Calmar, Information Ratio
  - Factor-specific: factor exposures, attribution (Brinson or regression-based)
  - Turnover and transaction cost drag

- **Benchmark**: should performance be measured in absolute terms, or relative to a benchmark (e.g., SPY, equal-weight index)?

- **Output format**: how do you want to consume results?
  - Python objects / DataFrames for further analysis
  - Plots (matplotlib / plotly)
  - HTML report
  - Jupyter notebook integration

---

## 9. Extensibility & Architecture Patterns

### Open questions

- **Abstraction style**: abstract base classes (ABC) or protocols (structural subtyping)?
  - ABCs enforce explicit inheritance and provide clear "what you must implement" docs
  - Protocols are more flexible (duck typing), easier to mock in tests

- **Plugin / registry pattern**: should components (strategies, data handlers, execution models) be discoverable via a registry, or just instantiated directly in a config/script?

- **Configuration**: how is a backtest configured?
  - Python dataclasses / typed config objects
  - YAML / TOML config files
  - Pure code (no config layer)

- **Parallelism**: do you ever need to run parameter sweeps (e.g., test 100 factor combinations) in parallel? If so, the backtester instance needs to be stateless / serializable.
